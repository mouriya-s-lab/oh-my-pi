# 需求原文

来源：会话 `01a16321-28cf-7321-ab54-493bcb67b954`（2026-10-22），用户原话，未改动。

## 起因

当前有个监控子进程过高占用的监控是怎么写的，好像会无限告警

4G阈值做成omomp配置文件可更改的，而不是写死，同时可以在project级被覆盖

250 ms 太频繁

## 方案

我之前自己在想的方案是，在omp宿主里面增加统一的进程fork记录在内存，随omp进程的退出杀掉，同时做完整的cpu，内存，io的记录，并在这个基础上做告警

windows怎么办？

我认为这个功能需要设计好严格的类型，仅针对这一块用ssot设计

我记得mouriya-s-lab有单独的fork，但是那个fork是用来做远程subagent的，那个功能单独在一个分支里保护后重新跟随上游最新版，然后本功能在omp fork里做。

我认为这个功能的本质是在规范化设计omp harness内部的进程组织，所以这实际上是一种架构+业务，而现在是业务实际上都存在，而三个os是三个不同的实现方案，中间要有合理的统一的抽象，ssot能帮你把各个实验都填在外围再看里面怎么弄好

## 决定

本来就应该是s1，乃至逃逸这件事根本不应该是这么做，想逃逸应该用plist和systemd，而不是harness代劳，这是完全错误的做法。为什么要考虑猜的进程？
