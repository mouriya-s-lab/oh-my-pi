# 登记

负责记下归属单位的嵌套、每个单位自己开出的围栏，以及每个进程属于哪个单位、承诺活多久、归属依据是什么、放在哪个围栏里；不负责起进程、终止进程、读用量，也不负责决定一个进程该用哪种承诺。

## 为什么

单独成为子模块：台账只用到父模块的身份与围栏类型，不需要平台的任何连接；平台也不需要知道谁属于谁。归属单位、围栏归属与进程登记放在同一个模块，因为它们共守"登记在册的进程都属于一个活着的单位，写明的围栏都是某个活着的单位开出的"这条不变量（``Registry`Table``）。

归属单位是一棵可嵌套的树，架构不规定层数：宿主、会话、工具调用是业务对单位的细化，架构只要求内层在外层之内开始、外层结束前内层已全部结束。收尾顺序由嵌套决定，不由谁先发现谁决定。

寿命承诺（``Registry`Policy``）由起进程的一方在登记时给出，不由台账事后推断：只有起进程的一方知道这是单位自己的进程、多个宿主共用的守护进程，还是用户有意放走的进程。承诺不随单位结束的进程不得写明围栏，这样 ``Platform`Kill`` 永远不会误伤它们。

放置（``Registry`Entry.fence``）与承诺分开：随单位结束该终止的进程也可以在围栏外（macOS 上的 MCP 服务器），收尾时按身份逐个终止。不让承诺推出放置：那样 MCP 服务器要么进错围栏，要么永远不被终止。

归属依据（``Registry`Membership``）分三支：宿主亲手起的、围栏收纳的、推断出来的。``Registry`Killable`` 只对前两支为真：推断可能把别人的进程算成自己的，终止的代价不可逆，所以推断出来的只记录、只计量，不终止。

一个单位至多开一个自己的围栏，围栏不嵌套：没有自己围栏的单位，它的进程可以写明放在某个外层单位的围栏里。不让单位"沿用"外层围栏再中途改写：围栏在单位开始后经 ``Registry`Fence`` 一次定下，之前登记的进程不受影响，因为它们各自写明了自己所在的围栏。

## 语义

台账与平台运行在同一个宿主进程内；宿主崩溃时台账消失。

单位由 ``Registry`Begin`` 开始，由 ``Registry`End`` 结束；``End`` 要求内层已全部结束，名下没有可终止的登记。可终止的登记怎样清掉由业务决定：在单位自己围栏里的由 ``Platform`Kill`` 一次终止，围栏外的按身份 ``Platform`Terminate``；两者都发生后，业务经 ``Registry`Drop`` 让台账跟上事实。

进程退出的事实来自平台，``Registry`Drop`` 只是台账跟上事实；撤销两次与一次效果相同。

围栏收纳的进程（`<Enclosed>`）继承 `<Owned>` 承诺并写明所在围栏；推断出来的进程（`<Inferred>`）以 `<Released>` 登记，不写围栏。
