# 平台

负责陈述操作系统的事实：起进程并随之开围栏、列围栏成员、按标记认进程、读用量、终止进程与围栏，以及这个平台的围栏能保证到什么程度；不负责决定哪些进程属于哪个单位，也不负责告警。

## 为什么

单独成为子模块：三个操作系统各自实现这一个模块就互换，父模块只需要它们共用的身份、标记、围栏与读数类型，不需要知道围栏在某个平台上是进程组、cgroup 还是作业对象。

围栏随 ``Platform`Spawn`` 诞生、随最后一个成员退出消失，没有单独的开与关：这是三个平台都能兑现的唯一原语（依据见父模块）。状态里的 `members` 只放有成员的围栏，`charged` 与 `peak` 随围栏一起消失；围栏消失后它的累计量不再可读，所以收尾前要先 ``Platform`Measure``。

`charged` 只累计 CPU 与 IO：已退出进程的内存不是任何时刻的占用，加进去会把死进程算成围栏"当前"内存。`peak` 是围栏整体的峰值内存，只有平台自己能给（Linux `memory.peak`、Windows 作业峰值提交内存），macOS 的每进程峰值不可相加，所以 `peak` 的定义域是 `members` 的子集。

``Platform`Marked`` 只认宿主盖的标记，不按父子关系推断；推断的理由见父模块。

## 语义

一个进程至多在一个围栏里；围栏之间没有包含关系；宿主自己所在的进程组或作业不是围栏。

进程可以在任何连接之外出生或退出：围栏里的进程自行派生后代时，`contained` 为真的平台上后代一定成为同一围栏的成员，为假的平台上后代通常成为成员但可以离开；进程自行退出时，它离开 `alive`、`marked` 与所在围栏的成员集，累计量计入该围栏的 `charged`，围栏空了就消失。这些变化由操作系统引起，不是宿主可以调用的连接，所以不写成操作；宿主经 ``Members``、``Marked`` 与 ``ProbeAll`` 事后得知，三者的结果都是取回那一刻的副本。

``Platform`Spawn`` 要了围栏却开不出来时（宿主已处于外层容器而外层不允许嵌套），进程照样起来，`enclosure` 为空；这不是失败，起进程的一方按无围栏登记。

``Platform`Describe`` 在整个宿主生命周期内返回同一个值。
