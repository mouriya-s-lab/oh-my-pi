# 进程治理

负责定义宿主起的进程怎样识别、怎样圈住、属于哪个归属单位、用量怎样读，并让三个操作系统在同一套连接下互换；不负责阈值、告警与保留历史，也不负责任何活过宿主的进程。

本模块只持有两个子模块共用的材料：进程身份、血统标记、围栏与它的能力、用量读数。操作系统的事实由 `platform/` 陈述，谁属于谁由 `registry/` 陈述；两者并列，互不引用，只共用本模块的类型。

## 依据

活过宿主的进程由操作系统的服务管理器（launchd、systemd、Windows 服务）拥有：它们的父进程是服务管理器，不是宿主（来源：launchd 与 systemd 的职责定义；omp 当前用两层 fork 与 detached 起守护进程，正是上游 #5684 里"强退宿主后开发服务器仍在跑"的来源，证据见 `evidence/spawn-sites.md`、`evidence/upstream-issues.md`）。所以宿主起的进程一律随它的归属单位结束而终止，没有"放走"这一承诺；要活过宿主，由起进程的一方向服务管理器提交声明，那是宿主之外的对象，本设计不建模。

宿主只在自己起进程的那一刻能拿到子进程的身份；eval 里用户代码起的子进程、shell 里两层 fork 留下的孤儿，宿主拿不到起进程事件（来源：证据 `evidence/spawn-sites.md`）。所以归属不能只靠起进程那一刻的登记，宿主要能事后认出自己的后代。

能证明血统的只有两样：宿主自己围栏里的成员（强平台由内核保证，macOS 上外人进不了宿主自己 `setsid` 开出的进程组），以及带着宿主盖在环境里的标记的进程。按父子关系推断不能证明：桌面应用启动的多个宿主共用同一个父进程，按父子关系会把兄弟宿主的进程算成自己的；环境标记对 Apple 系统自带的程序读不到（来源：证据 `evidence/spawn-sites.md`、`evidence/platform-containment.md`）。所以 ``Registry`Membership`` 只有围栏成员与标记两种事后依据，不推断；标记的结果是下界，写进语义。

进程号会复用，上游曾因此把宿主自己当作子进程的后代杀掉（来源：证据 `evidence/identity-and-usage.md`）。所以 ``Governance`Identity`` 由进程号加出生标记组成，每个连接都按这个身份操作。

macOS 的进程组随第一个进程 `setsid` 诞生，组长的进程号就是组号，不能先开空组再往里放；Linux 的 cgroup 与 Windows 的作业对象可以先开空容器，也可以在起第一个进程时一并开出（来源：证据 `evidence/platform-containment.md`）。所以围栏随一次 ``Platform`Spawn`` 诞生，与那次起的进程一一对应，最后一个成员退出就消失；三个平台都能兑现这一种原语，而"先开空围栏再放进程"只有两个平台能兑现。

Linux 的 cgroup 与 Windows 的作业对象让后代自动加入且不能自行离开，Windows 还由内核保证宿主死亡后终止全部成员；macOS 的进程组可以被 `setsid` 离开，宿主崩溃后没有机制清理（来源：证据 `evidence/platform-containment.md`）。所以 ``Governance`Capability`` 有两项：`guarantee` 决定宿主退出前要不要自己清围栏，`contained` 决定收尾与计量要不要用标记补找离开围栏的成员。

Windows 作业与 Linux cgroup 的累计用量含已退出成员，macOS 只能对活着的进程读用量，进程退出后用量并入父进程或丢失；CPU 与 IO 是累计量，内存是瞬时量，已退出进程的内存不是任何时刻的占用（来源：证据 `evidence/identity-and-usage.md`）。所以 ``Governance`Usage`` 把累计量与内存分开，``Governance`Reading`` 只给累计量标 ``Governance`Coverage``，内存永远只算活着的进程；围栏整体的峰值内存只有 Linux 与 Windows 给得出，macOS 的每进程峰值不可相加，所以 `memoryPeak` 可空。

宿主已处于终端或 IDE 开的作业或 cgroup 里时未必能再开围栏；macOS 上的 MCP 服务器因权限提示必须留在宿主的进程组里（来源：证据 `evidence/platform-containment.md`、`evidence/spawn-sites.md`，上游 #4987）。所以 ``Platform`Spawn`` 由起进程的一方决定要不要围栏，要了也可能开不出来，结局里围栏可空；没有围栏的进程收尾时按身份逐个终止。

上游 #5684 要求对整棵进程树限制资源，#12961 的维护者把观测与强制分开，先做登记（PID、启动时间、角色）与低频采样（来源：证据 `evidence/upstream-issues.md`）。所以本设计只定义归属、生命周期与计量的连接，不定义强制上限；归属单位的层级（宿主、会话、工具调用）是业务对"角色"的细化，架构只定义可嵌套的归属单位树。

## 为什么

身份、标记、围栏能力与读数放在根模块：操作系统的事实与归属台账都用到它们，而两者互不引用。不把 ``Registry`` 放进 ``Platform`` 之下：台账不是操作系统的内部细节，它只需要身份、标记与围栏的类型，不需要起进程、终止进程的连接。

围栏与一次 spawn 一一对应，不与归属单位对应，也不嵌套：一个围栏只有一个起源进程，起源进程只属于一个单位，围栏里后来出现的成员归属唯一，不需要再问"是外层的后代还是内层的后代"。代价是按单位计量要把该单位名下各围栏的读数相加，而不是读一个父容器；相加是纯函数，不损失语义。不让单位开围栏再让内层借用：借用之后围栏里的新成员归属不唯一，内层结束时既不能杀外层的围栏，也圈不出自己的后代。

三个平台实现同一个 ``Platform`` 模块，不写成三个模块：使用方按 ``Governance`Capability`` 分支，不按平台名分支。能力只保留设计里有人读的两项。不写"能否嵌套"：围栏不嵌套。不写"能否强制上限"：本设计不做强制。

不推断归属：推断的结果不能终止，只能告警，而告警对象可能是别人的进程。宿主自己的围栏与标记已经覆盖了能证明的全部血统，推断只会把不可靠的来源塞进告警。

宿主退出前的收尾是宿主的行为，不写在 ``Platform`` 里：平台只提供 ``Platform`Kill``，宿主按 ``Governance`Capability.guarantee`` 决定要不要调它。宿主崩溃后 `<Cooperative>` 围栏无人清理，本设计不另起监管进程：监管进程是另一个有自己生命周期的可部署物，本设计的契约只保证 `<Kernel>` 不漏、`<Cooperative>` 崩溃会漏。

计量不持有状态：读数是取回那一刻的副本，``Governance`Merge`` 把多个围栏与围栏外进程的读数合成一份，历史由消费方保留。峰值内存只在平台给得出时作为围栏事实交出，合成后不再有意义。

## 语义

``Platform`` 的状态是操作系统的事实，``Registry`` 的状态是宿主自己的台账；两者运行在同一个宿主进程内，宿主崩溃时台账随之消失，只有 `<Kernel>` 保证的围栏成员仍会被清理。进程可以在任何连接之外出生或退出，这些变化由操作系统引起，不写成连接；宿主经 ``Platform`Members``、``Platform`Marked`` 与 ``Platform`ProbeAll`` 事后得知，三者的结果都是取回那一刻的副本。

``Platform`Marked`` 的结果是下界：读不到环境的进程即使带着标记也不出现。`contained` 为假的平台上，离开围栏且读不到环境的进程无法被认出，本设计接受这一漏洞，不以推断弥补。

``Governance`Reading`` 的 `<LiveOnly>` 累计量在进程退出后会回落；两次取回之间出生又退出的进程在这种读数里不出现。
