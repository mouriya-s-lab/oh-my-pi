# 平台

负责陈述操作系统的事实：起进程并随之开围栏、列围栏此刻的成员、按环境里的单位身份认进程、读用量、终止进程、终止并释放围栏，以及这个平台的围栏能保证到什么程度；不负责决定哪些围栏或进程属于哪个单位，也不负责告警。

## 为什么

单独成为子模块：三个操作系统各自实现这一个模块就互换，父模块只需要它们共用的身份、单位、围栏与读数类型，不需要知道围栏在某个平台上是进程组、cgroup 还是作业对象。

围栏随 ``Platform`Spawn`` 诞生，在平台上一直保留到宿主调 ``Platform`Kill`` 释放它为止，成员全部退出后 `members(e)` 变成空集但围栏不蒸发：Linux 的 cgroup 与 Windows 的作业对象在成员退完后仍保留累计用量与峰值，这样正常跑完退出的命令在收尾前仍能经 ``Platform`Measure`` 读到；macOS 的进程组没有内核账本，成员退完后 ``Platform`Measure`` 返回零读数，收尾调 ``Platform`Kill`` 幂等无害。不要求调用方在 ``Platform`Measure`` 或 ``Platform`Kill`` 前保证围栏里还有活成员：进程随时可能在连接外退出，那样的前置契约在并发下无法遵守。

`charged` 的定义域是 `members` 的子集，与 `peak` 同构：只有平台具备围栏级累计账本（Linux cgroup、Windows 作业）时，围栏才在 `dom charged` 里，此时 ``Platform`Measure`` 给出 `<Complete>`；macOS 的进程组不在 `dom charged` 里，``Platform`Measure`` 只汇总此刻活着的成员并如实给出 `<LiveOnly>`。`charged` 只累计 CPU 与 IO：已退出进程的内存不是任何时刻的占用，加进去会把死进程算成围栏"当前"内存。

## 语义

一个进程至多在一个围栏里；围栏之间没有包含关系；宿主自己所在的进程组或作业不是围栏。

进程可以在任何连接之外出生或退出：围栏里的进程自行派生后代时，`contained` 为真的平台上后代一定成为同一围栏的成员，为假的平台上后代通常成为成员但可以离开；进程自行退出时，它离开 `alive`、`marked` 与所在围栏的成员集，若该围栏在 `dom charged` 里则它的累计量计入 `charged`。这些变化由操作系统引起，不是宿主可以调用的连接，所以不写成操作；宿主经 ``Members``、``Marked`` 与 ``ProbeAll`` 事后得知，三者的结果都是取回那一刻的副本。

``Platform`Spawn`` 要了围栏却开不出来时（宿主已处于外层容器而外层不允许嵌套），进程照样起来，`enclosure` 为空；这不是失败，起进程的一方按无围栏登记。

``Platform`Describe`` 在整个宿主生命周期内返回同一个值。
